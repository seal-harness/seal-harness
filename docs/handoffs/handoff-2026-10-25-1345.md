## 1. Objective

Make the gateway-API chat channels (Signal / Telegram, `src-chat-channels/`)
behave like the deleted in-process channels (`Seal.Channels.Loop`, removed in
`99ddc53`) for every slash command the user can type. `/bg` is done (PR #283);
`/tab`, `/new`'s arguments/rebind, and the Telegram command menu are not.

Why it matters: chat channels only speak the gateway HTTP/WS API now, so any
command the gateway does not implement — or refuses — is simply gone from a
user's phone, with no error that explains it.

## 2. Definition of Done

- [ ] **`/tab list`** replies with one line per tab (`<index>  <kind>  [label]`) or `no tabs`, from `GET /api/tabs`.
- [ ] **`/tab new`** inserts a provider tab (`POST /api/tabs/new`), replies `tab N created`, and does **not** change the conversation's session.
- [ ] **`/tab close N`** closes the tab (`POST /api/tabs/:idx/close`), replies `tab N closed`; failures reply `close failed: <e>`.
- [ ] **`/tab rename N <name>`** works (needs a gateway endpoint — see §8).
- [ ] **`/tab resume <sid>`** opens a tab bound to an existing session (needs a gateway endpoint — see §8), replies `tab N resumed`.
- [ ] **`/tab focus N`** keeps working through the existing `/N` path (regression test only).
- [ ] **bare `/tab`** keeps working (current tab of the conversation's session).
- [ ] **`/new -p <prov>` / `-m <model>`** mint the new session with those overrides.
- [ ] **`/new -r <repo>`** dispatches `SETUP_REPO` into the new session (`POST /api/sessions/:id/setup-repo`) and reports the clone result.
- [ ] **`/new`** rebinds the conversation's existing tab (if any) to the new session and replies the old-style line `new session <sid> (<prov>/<model>) — prior session <oldSid> kept in /session list`.
- [ ] **Telegram** registers the bot command menu at startup (list derived from the chat-visible commands).
- [ ] `/bg` and every existing test keep passing; `-Wall -Werror` and `hlint` clean for `src/`, `test/` **and** `src-chat-channels/`.
- [ ] Every DoD item above is pinned by a test that **fails before** the implementation.

## 5. Key Decisions & Rationale (do not undo without reason)

- **Chat commands are intercepted client-side; the gateway registry is not extended with channel-only commands.** `/bg` is not in the gateway registry, so `POST /send` still answers `unknown command: bg` for the web (pinned by a test in `test/Seal/Gateway/SendSpec.hs`). Rationale: `/bg` makes no sense for the web UI (it has tabs), and the user asked to keep web behaviour unchanged. Apply the same rule to `/tab` and the `/new` flags.
- **`/bg` uses a dedicated WS connection per bg session**, because `entry`/`ask` events are focus-filtered per connection while `activity` is all-subscriber. Do not try to deliver a bg turn over the conversation's connection.
- **Retired bg session ids are remembered (`bsKnown`, cap 32)** so the all-subscriber activity stream cannot leak a bg turn into `/watch`. Do not replace `bgOwnsSession` with "live sessions only" — there is a test that fails (`keeps a retired bg session out of watch mode`).
- **Chat asks are answered by plain text only for bg sessions**; foreground asks remain button/web-only (documented limitation). If you touch `answerPendingBgAsk`, keep the "earliest registration wins across sessions" rule (`paSeq`) — a test pins it (mutating the comparison makes it fail).
- **The gateway's `handleSend` refuses `TabCommand` on purpose** — the web has a sidebar. For chat channels, implement `/tab` in the loop over REST; do **not** remove the `Send.hs:581` guard (web clients rely on it).
- **Never** use `--no-verify`, never force-push. Repo rules: `.agents/…`/AGENTS.md.

## 8. Open Questions / Blockers

1. **`/tab rename` and `/tab resume` have no gateway endpoint.** Two options: (a) extend `POST /api/tabs/new` to accept an existing `session_id` (covers resume) and add `POST /api/tabs/:idx/rename {label}`; or (b) drop those two subcommands from the chat surface and reply "not supported from chat". Recommend (a) — both are ~15 lines in `API.hs` plus a test in `ApiSpec.hs`, and they unblock the web UI too. Ask the user before adding endpoints.
2. **`/new` rebind semantics.** `POST /api/sessions/:id/new` already rebinds the tab, but ignores `-p/-m` and labels the session `"web"`. Decide: extend that endpoint with optional `provider`/`model`/`channel` fields (recommended; one handler, one test), or mint via `/api/sessions/new` and accept that the old tab is not rebound (chat-only workaround, but then the web sidebar keeps showing the previous session).
3. **Telegram command list source.** Hard-code the channel-visible commands in the adapter, or add `GET /api/commands` to the gateway (names + descriptions from the registry+`bgHelp`/`watchHelp`)? The latter is DRY and gives the web a help source; the former is a 10-line change. Recommend the endpoint if help discoverability matters, otherwise hard-code.
4. **Should `/tab new` from chat also make the new tab the conversation's session?** Old behaviour: no (`TabNewCmd` inserted a placeholder and replied only). Keep old behaviour unless the user says otherwise.
