## Review gate outcome (v1 → v2)

Three reviewers (Architect, Security, CTO) reviewed v1. All returned
NEEDS-CHANGES. The core design (Option 1, vault-only token,
`RepoCredential` ADT unchanged, `vhPut` mirror of `generateDeployKey`,

three. The required changes were about **ordering, edge-case
completeness, and test feasibility** — not the core architecture.
Addressed in v2:

- **B2 (orphan-token ordering):** The `vhPut`-before-`upsertRepo`
  ordering (mirroring `generateDeployKey`) is kept, but the inert-orphan
  partial-failure window is documented in §3.5. If `vhPut` succeeds but
  `upsertRepo` fails, the vault holds an unreferenced token (inert —
  no consumer); the operator removes it via `/vault delete <key>`. Not
  a leak. (Alternative — `upsertRepo`-first — was rejected: it would
  create a repo descriptor pointing at a missing vault entry on
  `vhPut` failure, which is a worse failure mode for a user-supplied
  secret.)
- **B4 (PUT path ordering):** §3.3.4 now sketches the PUT token branch
  explicitly with `vhPut` BEFORE `upsertRepo repo'`, fail-closed 500
  on vault error.
- **B7 (defensive no-token-in-logs test):** §5.2 adds a test that
  captures the `globalLogIO` scribe during `POST /api/repos` with
  `token: "xyz"` and asserts no log line contains `xyz`. Regression
  guard against future body-logging middleware. (Confirmed: no
  request-body logging exists today — verified across `Server.hs`,
  `API.hs`, `Stream.hs`.)
- **B8 (reverse-proxy caveat):** §3.5 adds a deployment note: operators
  behind a reverse proxy must ensure access logs don't capture request
  bodies.
- **C1 (cross-layer test feasibility — registry persistence):** The
  `ApiTestHarness` fake `RepoRegistryHandle` has a no-op `rrhMutate`
  (POSTed repos aren't visible to the opcode's `uioCdRepoRegList`).
  The cross-layer test (§3.6) now specifies a **real
  `mkRepoRegistryHandle (tmp </> "repos.toml")`** (as `ApiSpec.hs:2588`
  does for the deploy-key PUT test), NOT the `ApiTestHarness` fake.
- **C2 (cross-layer test feasibility — SessionExec wrapping):** The
  `fakeUio` from `BinGhSpec.hs` is a `UntrustedIO` record, but the
  agent loop consumes a `SessionExec` (which wraps `UntrustedIO` in
  `UIOEnv`). §3.6 now specifies the `adMkSessionExec` override: the
  test sets `adMkSessionExec = Just (const (pure stubExec))` where
  `stubExec` carries a recording `UntrustedIO` (wrapped in

- **Q6 (PUT credential-kind-change edge case):** §3.3.4 now addresses
  the case where the operator switches credential kind on edit. When
  `srCredential repo /= srCredential old` (kind changed), the old vault
  key is `vhDelete`d (best-effort) and a token is REQUIRED (400 if

  unchanged, PUT without a token preserves the existing vault entry.

  pat/machine_user credentials" (all three reviewers concurred). Added

## 1. Problem

The `gh`/`git` BIN_EXEC credential-injection path (issue #123, branch
`feat/gh-bin-exec-credential-injection`) correctly *reads* a PAT from the
vault and injects `GH_TOKEN` (or `http.extraHeader` for `git`) into the
subprocess. But there is **no way to get a PAT into the vault via the "New
repo" form**. The form has a credential-kind dropdown (PAT / DeployKey /
MachineUser), but selecting `pat` shows only an advisory note — no input
field for the token value.

The deploy-key flow generates its secret server-side (`ssh-keygen` → vault
`vhPut`), so the user never types a secret. The PAT flow has no analog: a
PAT is generated by GitHub (out of the harness's reach), so the **user
must supply the token value** in the form, and the harness must store it in
the vault under a repo-specific key.

The user's only path today is to run `/vault add seal-pat-<id>` out-of-band
(typing the token into a hidden channel prompt) *before* creating the repo
— a two-step dance the form doesn't surface.

The hard requirement (unchanged): **un-encrypted secrets MUST NEVER be
written to disk** — the token goes to the vault (age-encrypted at rest)
and nowhere else. Never to `repos.toml`, never to the transcript, never to
debug logs (the redaction seam from #123 handles the last).

## 1a. Use Cases (WHO / WANTS / SO THAT / WHEN)

1. **Operator registers a PAT-credential repo in one step** — *As* an
   operator, *I want* to fill the "New repo" form, pick "Personal Access
   Token", paste the PAT value into a password field, and submit — having
   the harness store the token in the vault under a deterministic key and
   the repo descriptor in `repos.toml` — *so that* I can register a
   PAT-authenticated repo in a single form submission without a separate
   `/vault add` step, *when* I'm setting up a repo for `gh`/`git` PAT auth.
2. **Operator registers a MachineUser repo with the token in one step** —
   *As* an operator, *I want* the same single-step flow for a
   MachineUser credential (username + token), *so that* I don't need the
   out-of-band `/vault add`, *when* I'm setting up a bot-account repo.
3. **Agent runs `gh pr create` against a PAT-registered repo** — *As* an
   agent, *I want* `BIN_EXEC` with `binary="gh"` from inside a
   PAT-registered repo's workdir to authenticate via `GH_TOKEN` injected
   from the vault (the token the operator pasted in the form), *so that*
   `gh pr create` succeeds on the first try, *when* I finish work on a
   branch. (This is the #123 flow — this design makes the PAT *available*
   to it.)
4. **Operator's token never lands on disk un-encrypted** — *As* an
   operator, *I want* the PAT I paste in the form to go ONLY to the vault
   (age-encrypted at rest) — never to `repos.toml`, the transcript, debug
   logs, or any other file — *so that* the secret is protected at rest,
   *when* I register the repo.
5. **Operator's token is not echoed back by the API** — *As* an operator,
   *I want* the `POST /api/repos` response to carry only the repo
   descriptor (id, url, vcs_kind, credential `{kind, vault_key}`) — NOT
   the token value — *so that* a leaked response body or a browser-history
   capture can't expose the token, *when* the API responds.
6. **Operator updates a repo's PAT** — *As* an operator, *I want* to
   paste a new token into the edit form and have the harness overwrite the
   vault entry (same key) — *so that* I can rotate a compromised or expired
   PAT, *when* GitHub issues a new token. (The PUT path mirrors POST.)

## 2. Non-Goals

- **No token in `repos.toml` / `RepoCredential` ADT.** The persisted
  `SourceRepo` keeps only `cVaultKey :: Text` (a vault key name). The raw
  token lives only in the vault. The `RepoCredential` ADT is NOT extended
  with a token field — the token is handled only in the API layer (an
  ephemeral field extracted from the request body, never persisted).
- **No token in `RepoInfo` / `RepoInput` frontend types.** The
  `RepoCredential` TS interface (the persisted shape) keeps only
  `vault_key`. The token is a separate, create-only field (see §3.1).
- **No token in the API response.** `handleRepoCreate` / `handleRepoUpdate`
  return `repoInfoJson` (the descriptor) — no token field.
- **No token in the transcript.** The repo-create API path doesn't go
  through the ISA transcript; but the `repos.toml` audit-commit (the
  `bestEffortCommitRepos` `gitCommitAll`) must not capture the token
  either — it only commits `repos.toml`, which has no token field.
- **No `--token` flag for `/repo add`.** A `--token` flag would leak
  the token into shell history and `ps` output. Instead, `/repo add
  --cred pat` (or `--cred machine_user`) prompts the user to paste the
  token on stdin with **hidden input** (no-echo), mirroring the
  existing `/vault add` flow (`Vault/Commands.hs:312` uses
  `ccPromptSecret`, which in the CLI channel uses `getPassword` from
  haskeline with `*` masking — `Channel/Cli.hs:159-161`). The token
  goes from stdin → `ccPromptSecret` → `vhPut` → vault, never touching
  argv or disk. The CLI `/repo add` becomes a single-step flow matching
  the form.
- **No token re-display in the edit form.** The edit form does NOT
  pre-populate the token (it's not retrievable from the vault via the
  API without a new, dangerous endpoint). The operator pastes a new
  token only when rotating; otherwise the field is empty and the PUT
  omits the token (no vault change). This is the same UX as a password
  field — empty means "no change."

## 3. Design

### 3.1 The token field (frontend + API — create-only, ephemeral)

The token is a **create-time, write-only field** — it's sent to the
server, stored in the vault, and never returned. It's NOT part of the
persisted `RepoCredential` shape (frontend or backend). Two options for
where to put it:

- **Option 1: a top-level `token` field on the request body.** `POST
  /api/repos` accepts `{ id, url, vcs_kind, credential: {kind,
  vault_key, ...}, token?: string }`. The `token` is optional; when
  present and `credential.kind` is `pat` or `machine_user`, the server
  `vhPut`s it under `credential.vault_key`. When absent, the server does
  NOT touch the vault (preserving the out-of-band `/vault add` path).
  Pros: clean separation (the persisted `credential` object is unchanged
  in both the TS and Haskell types); the token is clearly ephemeral.
  Cons: a top-level field that's easy to forget to scrub from logs.
- **Option 2: a `token` field inside the `credential` object.** `POST
  /api/repos` accepts `{ ..., credential: {kind, vault_key, token?} }`.
  Pros: the token is visually associated with the credential.
  Cons: muddies the `RepoCredential` TS interface (which is also the
  GET response shape) — would need a separate `RepoCredentialInput`
  type to avoid implying the token is returned.

**Decision: Option 1 (top-level `token`).** The `RepoCredential` shape
(both TS and Haskell) is the *persisted* shape and stays unchanged. The
token is a separate, write-only request field. This is the same pattern
as `generate_key` (a top-level, create-time, write-only boolean that
triggers server-side key generation). The token is the PAT analog of
`generate_key`.

### 3.2 Frontend changes (`ReposView.tsx`)

1. **Add a password input** shown when `credKind === 'pat' || credKind
   === 'machine_user'` (the two token-bearing credential kinds). The
   field is a `<input type="password">` labeled "PAT" (for `pat`) or
   "Bot token" (for `machine_user`), with a placeholder like
   `ghp_...`. Mirror the `machine_user` Username row's placement
   (`ReposView.tsx:410-422`).
2. **Form state**: add a `token?: string` to the form state (the
   `useState` that holds `form`). Initialize empty. Clear it when
   switching credential kinds (so a PAT typed then switched to
   deploy_key doesn't leak into the payload).
3. **Validation** (`validateForm`, lines 138-147): require the token
   when `creating` and `credKind` is `pat` or `machine_user`. On edit
   (`editing`), the token is optional (empty means "no change" — don't
   send it, don't touch the vault).
4. **`handleSubmit`** (lines 149-202): when `creating` and the token is
   present, add `token: <value>` to the `payload: RepoInput`. (Extend
   `RepoInput` with `token?: string`.) When `editing`, add `token` only
   if non-empty (rotation). The field is sent over HTTPS (the gateway
   uses Warp with TLS in production; in dev it's localhost).
5. **Edit form**: the password field is present but EMPTY (no
   pre-population — the token is not retrievable). A `placeholder` like
   "Paste new PAT to rotate (leave empty to keep)" makes the UX clear.
6. **The advisory note** (lines 399-403) stays but moves below the token
   field (so the field is the primary interaction, not the note).

### 3.3 API changes (`API.hs`)

1. **`parseRepoFromBody` / `parseRepoWithId`** (lines 1447-1488): these
   build the `SourceRepo` (which has NO token field — correct, the ADT
   is unchanged). No change here.
2. **Extract the token at the `handleRepoCreate` level** (not in
   `parseRepoFromBody`, which returns the `SourceRepo`). The token is
   read directly from the raw JSON `Value` (like `genKey` is read at
   `API.hs:1302-1306`):
   ```haskell
   mToken <- case v of
     A.Object o -> case KeyMap.lookup (Key.fromText "token") o of
       Just (A.String t) | not (T.null (T.strip t)) -> Right (Just (T.strip t))
       Just A.Null                                   -> Right Nothing
       Just _                                        -> Left "token must be a string"
       Nothing                                       -> Right Nothing
     _ -> Right Nothing
   ```
3. **Store the token in the vault** when present and the credential
   kind is PAT or MachineUser. First, **validate** (adopting Open
   Question 1's resolution — 400): if `mToken == Just _` and the
   credential kind is `CredDeployKey`, return 400 `"token is only
   valid for pat/machine_user credentials"`. Then, after parsing the
   `SourceRepo`, in `handleRepoCreate` (between the `genKey` check at
   line 1310 and the standard-upsert at line 1332), add a
   PAT/MachineUser token branch:
   ```haskell
   if genKey && isDeployKey
     then {- existing deploy-key path -}
     else case mToken of
       Just _ | isDeployKey (srCredential repo) ->
         pure (errJson status400 "token is only valid for pat/machine_user credentials")
       Just token -> do
         mh <- readIORef (vrHandleRef (adVault deps))
         case mh of
           Nothing -> pure (errJson status500 "vault locked — run /vault unlock")
           Just vh -> do
             ePut <- vhPut vh (cVaultKey (srCredential repo)) (TE.encodeUtf8 token)
             case ePut of
               Left ve -> pure (errJson status500 ("vault put failed: " <> T.pack (show ve)))
               Right _ -> do
                 -- Standard upsert (the repo descriptor has only the vault key NAME).
                 eRes <- rrhMutate (adRepoRegistry deps) (upsertRepo repo)
                 ... -- existing broadcast + jsonCreated
       Nothing -> {- existing standard-upsert path (no token, no vault touch) -}
   ```
   This mirrors `generateDeployKey`'s `vhPut` (`API.hs:1961`) exactly.
   The vault-locked → 500 is the same error as the deploy-key path
   (`API.hs:1315`). The `repos.toml` write (`rrhMutate (upsertRepo
   repo)`) stores only `cVaultKey` — no token bytes. **Ordering:**
   `vhPut` BEFORE `upsertRepo` (matching the deploy-key path). If
   `upsertRepo` fails after `vhPut` succeeds, the vault holds an
   **inert orphan token** (unreferenced — no repo descriptor points to
   it; no `BIN_EXEC` path can retrieve it). The operator removes it
   via `/vault delete <key>`. This is the same partial-failure window
   the deploy-key path has (`generateDeployKey` → `upsertRepo`); it's
   accepted as best-effort (the registry mutation rarely fails — it's
   an atomic file write). See §3.5.
4. **`handleRepoUpdate`** (lines 1347-1379): mirror the token branch.
   The PUT path extracts the `token` from the raw JSON body (same as
   POST). The `repo'` preserve-server-state logic (lines 1371-1377,
   which preserves `srDeployKeyPublic`/`srKeyfilePath` for deploy keys
   when the credential is unchanged) is unaffected — the token is not
   in the `SourceRepo`. The token branch is inserted BEFORE the
   `rrhMutate (upsertRepo repo')` call (line 1378):
   ```haskell
   -- After the repo' preserve-server-state logic (lines 1371-1377):
   -- Validate token + deploy_key (same as POST).
   case mToken of
     Just _ | isDeployKey (srCredential repo') ->
       pure (errJson status400 "token is only valid for pat/machine_user credentials")
     Just token | not (isDeployKey (srCredential repo')) -> do
       -- Check if the credential kind changed (e.g. PAT → MachineUser).
       let kindChanged = srCredential repo' /= srCredential old
           mOldVaultKey = if kindChanged then Just (cVaultKey (srCredential old)) else Nothing
       mh <- readIORef (vrHandleRef (adVault deps))
       case mh of
         Nothing -> pure (errJson status500 "vault locked — run /vault unlock")
         Just vh -> do
           -- Best-effort delete the old vault key if the kind changed
           -- (the old entry is inert without a repo descriptor, but
           -- cleaning it up avoids orphan accumulation). vhDelete
           -- failure is swallowed (the old key may not exist).
           case mOldVaultKey of
             Just oldKey -> void (vhDelete vh oldKey)
             Nothing -> pure ()
           ePut <- vhPut vh (cVaultKey (srCredential repo')) (TE.encodeUtf8 token)
           case ePut of
             Left ve -> pure (errJson status500 ("vault put failed: " <> T.pack (show ve)))
             Right _ -> do
               eRes <- rrhMutate (adRepoRegistry deps) (upsertRepo repo')
               ... -- existing broadcast + jsonCreated
     Nothing -> do
       -- No token supplied on PUT.
       let kindChanged = srCredential repo' /= srCredential old
       if kindChanged
         then -- Kind changed but no token: the new vault key has no
              -- entry. Fail closed (400) — the operator must paste a
              -- token to re-authenticate under the new kind.
           pure (errJson status400
                  ("credential kind changed but no token supplied — paste a "
                 <> credentialKindLabel (srCredential repo')
                 <> " token to re-authenticate"))
         else -- Kind unchanged: preserve the existing vault entry
              -- (the PUT doesn't touch the vault).
           do eRes <- rrhMutate (adRepoRegistry deps) (upsertRepo repo')
              ... -- existing broadcast + jsonCreated
   ```
   **Ordering:** `vhPut` BEFORE `upsertRepo repo'` (same as POST),
   fail-closed 500 on vault error. **Credential-kind-change edge case
   (reviewer Q6):** when `srCredential repo' /= srCredential old`
   (kind changed), the old vault key is `vhDelete`d (best-effort) and
   a token is REQUIRED (400 if absent — the new vault key has no
   entry). When the kind is unchanged, PUT without a token preserves
   the existing vault entry. `vhDelete` is the vault's delete method
   (`Vault.hs` — verify it exists; if not, add it mirroring `vhPut`).
5. **The API response** (`repoInfoJson`) is unchanged — it returns the
   `SourceRepo` descriptor (id, url, vcs_kind, credential
   `{kind, vault_key, username?}`), no token field. Confirmed at
   `API.hs` `repoInfoJson`.

### 3.5 Security analysis

- **No un-encrypted secret on disk.** The token goes: HTTPS request body
  (in memory, parsed by `A.decode`) → `vhPut` (vault, age-encrypted at
  rest) → nowhere else. Not `repos.toml`, not the transcript, not a log.
  The `bestEffortCommitRepos` audit-commits `repos.toml` only — which
  has no token field.
- **No token in the API response.** `repoInfoJson` returns the
  `SourceRepo` (no token field by construction). The response body
  cannot leak the token.
- **No token in debug logs.** The `logExecDebug` redaction seam from
  #123 redacts `GH_TOKEN`/`GITHUB_TOKEN`/`http.extraHeader`. The
  repo-create API path doesn't go through `logExecDebug`, and
  **confirmed: the gateway does NOT log request bodies** (verified
  across `Server.hs`, `API.hs`, `Stream.hs` — no
  `globalLogIO`/`putStrLn`/`traceM` calls on request bodies; no WAI
  request-logging middleware). No scrubbing seam is needed. A
  defensive test (§5.2 #7) captures the `globalLogIO` scribe during a
  POST and asserts no log line contains the token — a regression guard
  against future body-logging middleware.
- **Orphan token on partial failure (reviewer B2).** If `vhPut`
  succeeds but `upsertRepo` fails (registry write/IO error), the vault
  holds a token with no repo descriptor. The orphan is **inert** — no
  `SourceRepo` references its vault key, so no `BIN_EXEC` path can
  retrieve it. The operator removes it via `/vault delete <key>`. Not
  a leak. This is the same partial-failure window the deploy-key path
  has (`generateDeployKey` → `upsertRepo`); it's accepted as
  best-effort (the registry mutation rarely fails — it's an atomic
  file write).
- **Reverse-proxy / access-log caveat (reviewer B8 — operator
  deployment note).** Operators running the gateway behind a reverse
  proxy (nginx/Caddy/Traefik) must ensure access logs do NOT capture
  request bodies. The `POST /api/repos` body carries the PAT in the
  `token` field. The harness code never logs the body, but a proxy
  body-capture directive would expose the token in proxy logs.
- **The token in the HTTP request body is in memory on the harness for
  the duration of the request.** This is the same residual as the
  deploy-key passphrase (generated in memory, `vhPut`, then GC'd). No
  disk. The TLS boundary (production) protects the wire; in dev
  (localhost) it's local loopback.
- **Vault-locked fails closed.** If the vault is locked, `vhPut` fails
  → 500 "vault locked — run /vault unlock". The repo is NOT created (no
  `upsertRepo` call). The operator unlocks and retries. (Same UX as the
  deploy-key path.)
- **Rotation overwrites the vault entry.** `vhPut` is an upsert (the
  vault is a key→value map; `vhPut` replaces the value for an existing
  key). A rotation PUT with a new token overwrites the old one. No
  stale-token-on-disk risk (the vault is the single source of truth).

### 3.6 The gateway-level integration test (the user's request)

The user asked for a gateway-API-level integration test that verifies
the full PAT flow without hitting GitHub: POST `/api/repos` with a PAT
token → the token lands in the vault → run `BIN_EXEC` with
`binary="gh"` → capture the `gh` command the opcode would execute →
assert `GH_TOKEN=xyz` is in the env extras. No real `gh` binary, no real
GitHub.

This is a cross-layer integration test: **API → vault → opcode → exec
seam**. The existing `ApiTestHarness` CANNOT be used as-is (reviewer
finding C1+C2): its fake `RepoRegistryHandle` has a no-op `rrhMutate`
(POSTed repos aren't visible to the opcode's `uioCdRepoRegList`), and
its `adMkSessionExec = Nothing` means the agent loop builds a REAL
`UntrustedIO` (which would actually execute `gh`). The test needs:

1. **A real `mkRepoRegistryHandle (tmp </> "repos.toml")`** (as
   `ApiSpec.hs:2588` does for the deploy-key PUT test) — so POSTed
   repos persist and the opcode's `uioCdRepoRegList` finds them.
2. **A fake vault** (`makeFakeVaultRuntime`) — the test asserts
   `vhGet` returns the token.
3. **A `adMkSessionExec` override** — `adMkSessionExec = Just (const
   (pure stubExec))` where `stubExec :: SessionExec` carries a
   **recording `UntrustedIO`** (the `fakeUioRecording` pattern from
   `BinGhSpec.hs:99-115`, wrapped in `mkTestUIOEnv` per
   `ApiSpec.hs:3238`). The recording `UntrustedIO`:
   - Returns a canned `remote.origin.url` (matching the registered
     repo's URL) from `uioBinExec` for the pre-flight `git config --get
     remote.origin.url`.
   - Records the `gh` exec call (the `uioBinExecEnv` call with
     `("GH_TOKEN", "xyz")` in extras) and returns a canned success.
   - Does NOT actually execute `gh` (no real binary, no GitHub).
4. **A mock LLM script** (via `setScript`) that emits a `BIN_EXEC`
   tool-use with `binary="gh"`, `args=["pr","create"]`.

The test body:
1. Build `ApiDeps` with the real `mkRepoRegistryHandle` + the fake
   vault + the `adMkSessionExec` override. Build `apiApp deps'`. (This
   is a custom `ApiTestEnv` — NOT `runApiTest`; the test constructs
   `ApiDeps` itself, mirroring `ApiSpec.hs:3192-3273` which already
   does this for the stub-`SessionExec` repo-agent test.)
2. POST `/api/repos` with `{ id: "test", url:
   "git@github.com:owner/test.git", vcs_kind: "github", credential:
   { kind: "pat", vault_key: "seal-pat-test" }, token: "xyz" }`.
3. Assert the response is 201 + the descriptor (no token in the
   response body — `repoInfoJson` has no token field by construction).
4. Assert the vault now has `"seal-pat-test" → "xyz"` (via `vhGet` on
   the fake vault handle).
5. Assert `repos.toml` (read the real file) does NOT contain `"xyz"`.
6. Create a tab, set the mock LLM script to emit `BIN_EXEC gh pr
   create`, send the message.
7. Assert the recorded exec (from the recording `UntrustedIO`)
   used `uioBinExecEnv` with `("GH_TOKEN", "xyz")` in env extras.
8. **Defensive:** capture the `globalLogIO` scribe during the POST
   and assert no log line contains `"xyz"` (regression guard —
   reviewer B7).

This test lives in a new `test/Seal/Gateway/PatIngestionSpec.hs` (the
reviewer confirmed `ApiIntegrationSpec.hs` is deploy-key-specific and
architecturally different — it uses real exec; this uses stub exec).
Run in local mode only initially (the token-in-env injection is
identical on both planes per #123 design §3.6; remote-mode parity is
a bonus, not essential for v1).
